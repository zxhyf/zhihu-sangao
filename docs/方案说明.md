# 智护三高 · 方案说明

> 第二届全国人工智能应用创新大赛 · 通用赛道（命题方向「让 AI Agent 赋能千行百业」· 领域：医疗）
> 本文为作品说明书，配套文件：`README.md`（运行说明）、`docs/智护三高_参赛作品说明.pptx`（演示文稿）、`docs/演示脚本.md`（3 分钟录屏脚本）。

## 一、命题与一句话方案

**命题**：面向高血压、高血糖、血脂异常（"三高"）人群及其家庭，做一个能读懂零散健康数据、生成个性化追踪方案、并在安全边界内给出可执行建议的 AI Agent。

**一句话**：让患者不用先学会用 App，只要说一句「今天血压 150/95」，系统就把数据记下来、看懂趋势、并安排好明天具体吃什么、做什么。

**与官方命题的对应**：通用赛道要求"围绕真实业务痛点，形成具备**可验证智能体交互能力**的 AI 应用解决方案"。本作品的可验证性体现在三处——
① 对话即交互，每一次输入都有可见的思考链路与结构化产出；
② 所有数值来自本地数据库与确定性工具，不依赖模型记忆；
③ 73 项自动化测试可在评审现场重跑。

## 二、问题定义：三个"看不见"

| 看不见 | 具体表现 | 后果 |
|---|---|---|
| 看不见交叉影响 | 三高常共病、多药同服，但分科管理 | 噻嗪类升糖升尿酸、β 阻滞剂掩盖低血糖、他汀+贝特增肌病风险，都没人说 |
| 看不见趋势 | 手写本、纸质单、不同品牌设备 | 只有孤立数字，没有均值、方向、异常次数 |
| 看不见执行 | "少盐少油多运动" | 患者回家不知道明天早餐吃什么，方案落不了地 |

再加上随访断链（门诊 3 分钟、两次门诊之间三个月）与依从性差（记不住、看不到效果、没人反馈），
共同构成三高管理的真实缺口。

## 三、方案总览

### 3.1 交互：Chat-first

打开即对话，不做功能菜单迷宫。左侧同步呈现档案、指标快照、今日任务，右侧对话区承载全部操作。
每条回复下方可展开「依据」，看到引用了哪本指南的哪一节。

### 3.2 能力链

```
用户一句话（或粘贴一张检验单）
  → 安全网关（红旗症状 / 处方红线，命中即锁定输出）
  → 意图识别（记录 / 检验单 / 趋势 / 方案 / 报告 / 用药 / 知识问答）
  → 实体抽取（指标、数值、单位、时间、场景、药名）
  → 生理校验 → 结构化入库（SQLite）
  → 受控工具调用（趋势、方案、报告、药物联动）
  → 知识库检索（BM25，可溯源）
  → 大模型叙事（只说"怎么说"，数字来自工具）
  → 结构化输出（卡片 + 来源 + 免责声明）
```

**检验单的"暂存—确认"闭环**：粘贴一份化验单文字后，系统逐项识别血糖、糖化、血脂四项，
给出参考范围与风险等级，但**不直接写库**；用户勾选确认后才入库，来源标记为 lab，
可回溯"这条数据是从哪张单子来的"。这解决的是 OCR 场景最难的一步——识别错误不能被静默接受。

### 3.3 技术栈与工程取舍

| 选择 | 理由 |
|---|---|
| 纯 Python 标准库 + 原生 JS | 评审拿到即可运行，不需要装依赖、不需要构建、不怕网络环境 |
| SQLite 本地存储 | 健康数据敏感，默认不出本机；也便于演示"数据不足就说不足" |
| 自研 BM25 检索 | 11 篇文档规模下，向量库是过度设计；BM25 可解释、可调试、可现场演示 |
| DeepSeek 可选 + 本地降级 | 断网、限流、Key 失效都不影响功能，只有措辞变简单 |

### 3.4 适老化与用药安全提示

**大字模式覆盖的是「输出」，不只是输入框旁边那句话。** 点「A+」后：
- 基准字号 15px → 19px，行高 1.65 → 1.8，侧栏同步加宽到 372px
- **所有结果卡片**一起放大：指标数值（27→34px）、方案时间轴、统计格、药物联动规则、报告章节、来源片段、曲线刻度、提示条
- 保留系统「减少动态效果」偏好，动画可关

**用药安全提示是结构性的，不是模型的自觉。** 只要一轮对话涉及用药（联动检查 / 用药记录 / 用药清单 / 周报），
后端就在返回的卡片列表里追加一个不可折叠的提示条，内容固定为四条 + 一句结论：

1. 以上内容用于帮助你准备与医生的沟通，不构成用药建议，也不能替代医生或药师的判断
2. **请严格按医生处方服药**：不自行加量、减量、换药或停药；漏服后不要自行补双倍剂量
3. 同时服用其他药物、保健品或中成药时，请务必告知医生或药师
4. 出现头晕、心慌、水肿、肌肉酸痛、黑便、尿量明显减少等不适，请尽快就医

> 结论行固定为「本建议不构成诊疗意见，请遵医嘱。」

这样即使大模型这轮回答忘了提，用户看到的界面上也一定有；换模型、换提示词都不会失效。

## 四、两个创新点（按要求讲透）

### 创新点一：把「药物—代谢」联动做进规则库

这是单病种 App 的结构性缺口：它们的知识库只覆盖自己那一科。

本项目把三科的常用药放在同一张表里，用「用户实际在吃什么」驱动检索，输出"需要关注什么 / 需要监测什么 / 该向医生问什么"：

| 组合 | 交叉点 | 系统动作 |
|---|---|---|
| 噻嗪类 + 磺脲类 | 升糖、升尿酸 | 提示同步监测血糖与尿酸，复诊时说明用药组合 |
| β 阻滞剂 + 胰岛素 | 掩盖低血糖（只留出汗） | 列为高风险：睡前加测、随身带葡萄糖、家人知情 |
| 他汀 + 贝特 / 大环内酯 / 西柚汁 | 肌病、肝损 | 提示复查 CK 与肝功能，出现肌痛立即就医 |
| ACEI/ARB + 螺内酯 / 低钠盐 | 高钾血症 | 用药 1 周内复查血钾，慎用低钠富钾盐 |
| NSAIDs + 降压药 + 利尿剂 | "三重打击"致急性肾损伤 | 避免自行长期止痛，疼痛先咨询 |

规模：**40 种常用药、31 条联动规则**，每条都能指回指南或说明书（`knowledge/med_rules.json`）。

**它为什么难被抄**：不是规则数量，而是"规则 + 谁在吃什么 + 用户自己的检查结果"三者联动。
系统会读你的用药清单和你最近的血糖/血钾记录，再决定提示的轻重。

### 创新点二：从「记录」到「明天照做就行」

同一句"多运动"，两种交付方式：

- ❌ 少盐少油、适当运动、保持心情愉快
- ✅ 19:00 快走 30 分钟（约 3000 步，能说话但唱不了歌）；做菜只用 1 勺酱油，汤不喝完；21:00 睡前测一次血压并记录

方案受**真实约束**驱动，而不是模板填空：

| 约束 | 方案如何变 |
|---|---|
| 会不会做饭 | 不做饭 → 便利店组合（无糖酸奶 + 全麦面包 + 水煮蛋）+ 食堂点菜话术 |
| 预算 | 紧 → 鸡蛋、豆腐、白菜、鸡胸肉，蛋白质一样够 |
| 口味 | 偏咸 → 分两步减盐，每两周减 1/4，味觉会适应 |
| 作息 | 起床 6:30 → 任务卡从 6:30 开始排 |
| 共病 | 合并糖尿病 → 增加餐后 2 小时血糖任务、主食定量、先菜后饭 |

输出形态：7 天 × 每天 11 项（测量 / 三餐 / 加餐 / 服药 / 运动 / 睡前），带时间、克数、做法与提醒。

## 五、安全边界（医疗类作品的生命线）

| 机制 | 触发条件 | 行为 |
|---|---|---|
| 红旗拦截 | 胸痛、呼吸困难、卒中征象、意识改变、酮症、消化道出血、胰腺炎、高血压急症（8 类） | **跳过全部建议生成**，直接输出 120 指引与等待救护车的注意事项 |
| 数值急症 | 血压 ≥180/110、血糖 <3.9 或 ≥16.7、TG ≥5.6 | 先留记录，再给急救提示，不自行加药 |
| 处方红线 | 加/减/停/换药、调剂量、自行断药 | 拒绝并给出复诊准备清单，不给任何剂量建议 |
| 工具白名单 | 未注册的工具调用 | 直接拦截（连参数都不进入执行） |
| 数据校验 | 生理边界越界、收缩压≤舒张压 | 拒绝入库并提示检查单位 |
| 用药提示 | 任何涉及用药的回答（联动检查 / 用药记录 / 用药清单 / 周报） | 由系统**结构性附加**提示条：不构成用药建议、不自行加减停药、出现哪些症状要就医，并明确「请严格遵医嘱服药」 |
| 统一免责 | 所有回复 | 「本建议不构成诊疗意见，请遵医嘱。」 |

**明确不做**：疾病诊断 · 开具处方 · 调整药物剂量 · 替代医生 · 急救判断 · 承诺疗效。

### 5.1 权限与数据完整性（第二轮加固）

原型阶段收到的最重要一条评审意见是"别把它当成已经能上线的系统"。据此我们补了七项：

| 风险 | 加固做法 | 效果 |
|---|---|---|
| 越权读取他人数据 | 身份只来自服务端会话，**删除 URL 中的 user 参数**；无密码时强制只监听本机 | 外部无法通过改参数读到别人的记录 |
| 知识库被随意改写 | 所有 `/api/*` 需登录；上传限 2 MB、限类型；删改与清空写审计日志 | 知识库直接影响回答，必须受控 |
| 打卡重复计数 | 唯一键「药物 + 日期 + 时段」，重复点击返回 `already_done` | 依从率不会再超过 100% |
| 未知药物污染统计 | 不在用药清单的药直接拒绝（400 + `unknown_med`） | 临时用药需先登记，统计口径干净 |
| 合成数据被误当病历 | 侧栏常驻「演示数据（合成）」提示条，可一键只清演示数据 | 评委和用户随时知道数据来源 |
| 一键清空太危险 | 必须传 `confirm=CLEAR`；区分"只清演示"与"全部清空" | 误触不会丢数据 |
| 档案字段乱填 | 身高 100–220、出生年份、作息 HH:MM、文本长度等字段级校验 | 脏数据进不了方案生成 |

同时保留 `data/audit.log`（JSONL，512 KB 轮转）记录登录、知识库变更、清空等操作。

## 七、数据来源

见 `knowledge/sources.json`（15 条台账）与 PPT 第 3–4 页。核心为：

- 临床指南 A 类：中国高血压防治指南（2024 修订版）、中国糖尿病防治指南（2024 版）、中国血脂管理指南（2023 年）、中国居民膳食指南（2022）、国家基层高血压/糖尿病防治管理指南
- 报告 B 类：中国心血管健康与疾病报告、中国居民营养与慢性病状况报告（2020 年）、IDF Diabetes Atlas
- 数据集 C 类：CHARLS、NHANES（方法学验证）
- 药品 D 类：NMPA 说明书、DailyMed
- 用户侧 E 类：手动录入 + 检验单 OCR + 对话抽取（微信蓝牙 API 规划中）

**合规**：指南全文受版权保护，知识库为内部要点整理、不整篇转载；对外材料按「名称 / 版本年份 / 发布机构 / 获取日期」标注。

## 八、落地路径

1. **社区卫生服务中心**：嵌入家庭医生签约与三高共管随访，作为医生的随访助手
2. **药店慢病管理**：购药提醒 + 依从性管理，药师端可见药物联动提示
3. **体检机构**：异常指标检后随访，转化路径最短
4. **子女端订阅**：远程看板与异常提醒，付费意愿最强

政策抓手：「三高共管、六病同防」是国家与多省正在推进的基层慢性病一体化服务模式，
本项目卡的正是它的信息化缺口——基层医生需要的不是三套系统，而是一次随访同时看清三高 + 用药 + 依从性。

## 十、局限与自我批评

1. **未做真实临床验证**：所有安全规则来自公开指南，未经本院医生逐条审核，属于工程实现而非医学结论。
2. **图片 OCR 未接入**：检验单目前支持"粘贴文字"录入（解析 → 人工勾选 → 入库），
   拍照直接识别需要接 OCR 服务或用户先用手机「提取文字」，这一步在下一阶段完成。
3. **个体化目标缺失**：系统只提示"是否超出指南参考范围"，不计算个人达标率——这是刻意的保守，避免越界。
4. **样本量小**：演示数据为合成数据，真实用户随访尚未开始。
5. **多用户与权限**：当前为单用户本地运行，家庭多成员与医生端权限模型待设计。

这些局限不影响作品的可运行性与创新点，但会在答辩中主动说明。
